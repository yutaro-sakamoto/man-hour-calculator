# 知見を貯めて、次に効かせる

man-hour-calculator では**これをやらなかった**。踏んだ穴は commit message と
`.claude/rules/` と CI のコメントに散らばっていて、拾い直すのに丸 1 日かかった。
**次のプロジェクトでは最初から入れる。**

要点は 1 つ。**書くだけでは効かない。昇格させる。**

## 昇格の段

| 段 | 形 | いつ上げるか | 守られかた |
|---|---|---|---|
| 0 | その場で直す | — | 忘れる |
| 1 | `JOURNAL.md` に 1 件書く | 踏んだその日 | 検索すれば出る |
| 2 | `AGENTS.md` / `.claude/rules/` に書く | **2 回目に踏んだら** | エージェントが読む |
| 3 | **機械の検査にする** (テスト / lint / `check-sync.sh`) | 3 回目、または重いとき | 破れば落ちる |
| 4 | `dev-skills/` に移す | **別のプロジェクトでも踏んだら** | 次の開発に効く |

段 3 に上がったものだけが本当に守られる。段 1 と 2 は、**段 3 に上げる候補を
貯める場所**でしかない。そう思って書く。

### 段 3 に上げられるか迷ったとき

「この決めごとを破ったコードは、どう書かれるか」を 1 つ思い浮かべて、
それを `grep` で見つけられるか考える。見つけられるなら `check-sync.sh` に
入れる ([docs-spec-drift](../docs-spec-drift/))。

実例:

| 段 1 で書いたこと | 段 3 でどうしたか |
|---|---|
| ABI の版が 3 か所にある | 3 つを grep して突き合わせる |
| Kani のハーネスを表に書き忘れる | ソースから名前を集めて文書を検索 |
| `.cfg` に INVARIANT が無いと TLC が緑になる | `grep -q '^INVARIANT'` |
| 外部にアイコンを足してしまう | E2E で外部リクエストを 0 件に固定 |
| 最適化が静かに外れて配布物が出る | CI で `--require-wasm-opt` |
| 空の SBOM を配った | 件数 0 なら落とす |

## 書きかた

`docs/JOURNAL.md` に**追記だけ**する。新しいものが上。1 件は 6 行。

```md
## 2026-09-21 — npm run check の出力を grep で絞って読み違えた

- 分類: ci / 読み違い
- 症状: Prettier の `[warn]` を見落とし、失敗を「成功」と報告した
- 原因: 出力を `grep -E 'error|fail'` で絞った。警告は別の語で出る
- 手当て: `tail` で見る。AGENTS.md に 1 行足した
- 昇格: rules
```

`昇格:` が要 (機械で数える)。取る値は 5 つだけ。

| 値 | 意味 |
|---|---|
| `未` | まだ何にもしていない。**これを数える** |
| `rules` | `AGENTS.md` か `.claude/rules/` に書いた (段 2) |
| `機械` | テスト / lint / `check-sync.sh` にした (段 3) |
| `skill` | `dev-skills/` に移した (段 4) |
| `一過性` | 上げる価値が無いと判断した。**判断したことを残す** |

`一過性` を用意しておくのが効く。無いと、上げられないものが `未` に溜まって
一覧が読めなくなり、仕組みごと死ぬ。

### 何を書くか

書く:

- **読み違い** (成功と失敗を取り違えた、出力を絞りすぎた)
- **環境の地雷** (apt の版が古い、Windows のパスの綴り、0 始まりの添字)
- **設計の判断と、その理由** (計算をクライアントに固定した、async にしなかった)
- **検査をすり抜けた穴** (仕様がモデル化していない対象があった)
- **やらないと決めたこと**

書かない:

- ふつうのバグ。**回帰テストを添えれば、テストが記録になる**
- 調べれば分かること (API の使い方)

## 道具

`assets/journal.sh` を `scripts/` に置く。

```sh
./scripts/journal.sh new      # 雛形を追記してエディタで開く
./scripts/journal.sh open     # 昇格: 未 の件数と一覧
./scripts/journal.sh stats    # 分類ごとの件数 (どこで転びやすいか分かる)
```

### `/learn` コマンド

その場で書かせる。`assets/commands/learn.md` を `.claude/commands/` に置く。

```
/learn                 # このセッションで踏んだものを書き出す
/learn <一行の要約>    # それについて書く
```

エージェントに書かせると、**自分が忘れている読み違いまで拾う**。
そのかわり「ふつうのバグは書かない」「推測で書かない」を明示しておく。

### 未昇格を数える Stop フック

`assets/journal-check.sh`。設計は `check-sync.sh` と同じ考え方。

- **閾値を超えるまで何も言わない** (既定 5 件)。毎回出ると読まれなくなる
- モデルを使わない。`grep -c` だけ
- 止めない。`additionalContext` を出すだけ

```json
{ "hooks": { "Stop": [{ "hooks": [
  { "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/journal-check.sh", "timeout": 10 }
]}]}}
```

## いつ書くか

| 機会 | 何を |
|---|---|
| CI が落ちて原因が環境だったとき | **必ず書く。** いちばん忘れる種類 |
| 「あれ、さっき直したはずでは」と思ったとき | 読み違いを書く |
| PR をマージしたとき | 設計判断を 1 行 |
| 形式手法が穴を見つけたとき | すり抜けた理由を書く (どの対象をモデル化していなかったか) |
| リリースで失敗したとき | 必ず書く。タグは打ち直せない |

**「直したから覚えている」は 2 週間もたない。** 直した直後が書きどき。

## プロジェクトを跨ぐ (段 4)

新しいプロジェクトを始めるとき、前のプロジェクトの `JOURNAL.md` の
`昇格: 未` と `昇格: rules` を読み返す。**2 つ目のプロジェクトでも出たものは、
`dev-skills/` のどれかに書き足す。**

1 回だけのものは移さない。1 回のものを全部移すと、スキルが読めない長さになって
誰も (自分も) 読まなくなる。

```sh
# 前のプロジェクトから、上げ損ねたものを拾う
grep -B 5 '昇格: 未' ../previous-project/docs/JOURNAL.md
```

## この仕組み自体が死ぬ兆候

- `昇格: 未` が 20 件を超えている → 昇格の基準が厳しすぎる。`一過性` を使う
- 3 週間書かれていない → `/learn` を呼ぶ機会が決まっていない。
  PR マージ時に呼ぶことにする
- 書いてあるのに同じ穴を踏んだ → **段 2 で止まっている。段 3 に上げる**
