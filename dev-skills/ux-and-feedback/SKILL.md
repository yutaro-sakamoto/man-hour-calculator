# 画面とフィードバック導線

フレームワークを入れずに素の DOM で作ると、**再描画の作法を自分で決める**
必要がある。そこを決めておけば、あとはずっと楽になる。

## 毎回作り直す。そのかわり持ち越すものを明示する

差分更新はしない。**作り直すと失われるもの**を列挙して、明示的に持ち越す。

| 失われるもの | 持ち越しかた |
|---|---|
| 焦点とキャレット | `data-focus` に鍵を付けて、描き直したあと復元する |
| `<details>` の開閉 | 状態 (`state.openPanels`) に持つ |
| 窓 (モーダル) | 状態から組み立てる。`<dialog>` は使わない |
| **書きかけの入力** | クロージャではなく状態に置く |

最後がいちばん刺さった。接続先のトークンを入力中に、**関係のない再描画で
消えていた**。クロージャに持つと、そのクロージャごと作り直されて消える。

## 数値入力でキャレットが飛ぶ

`type="number"` は**キャレットの位置を持ち越せない**。`type` を一時的に
`text` にしても、戻した時点で選択が消える (確認済み)。

1 打鍵ごとに作り直すと、`125` と打ったつもりが `521` になる。

**値だけを変える操作と、構造が変わる操作を分ける。**

```ts
actions.edit(...)    // 値だけ。**その場では描き直さない**
actions.mutate(...)  // 構造が変わる。描き直す
```

## API を叩く欄を `input` で拾わない

1 打鍵ごとに書き込みが飛び、応答の届く順によっては文字が落ちる。
名前のような欄は**確定したときだけ**送る (`change` / blur)。

## 初めて使う人が詰まる場所

空の状態で開いたときに、**次に何をすればよいかが画面に書いてある**こと。

- 空のリストに「まず◯◯を作る」と出す。空白のまま放置しない
- 例のデータを 1 件入れられるボタンを置く
- 初回だけ出る説明は、閉じたら覚える
- **破壊的な操作の前に問い返す** (`confirm`)。取り消せない操作は必ず

E2E で確認ダイアログを扱うときは `page.once("dialog", …)` を**先に**置く。

## 目を引かせる場所を 1 つに決める

一覧では「遅れているもの」を先頭に出し、強調する。

```rust
pub fn severity(self) -> u8 {   // 小さいほど先に出す
    match self {
        Self::Late => 0,
        Self::BehindPace => 1,
        Self::AtRisk => 2,
        ...
    }
}
```

**判定を 1 か所に置く。** サーバの一覧と画面の表示で食い違わせない。
「遅れている」の定義 (期限に対して / ペースに対して) も 1 か所に書く。

見積もりにも申告にも誤差があるので、**少しの差で赤くしない**。
許容幅 (`PACE_TOLERANCE = 0.10`) を定数に置いて、名前で意図を示す。

## 出さない情報を決める

- 分からないものは「分かったふり」をしない。控えが古ければ `Unknown` を出す
- 担当者のいないものを黙って誰かに押し付けない。「未割当」という仮の枠に
  まとめて、画面にもそう出す

**データの欠けを UI で埋めない。** 埋めると、間違ったまま意思決定される。

## 配色とダークモード

外部のフォント・アイコンを入れない前提だと、CSS 変数 + `color-scheme` で足りる。

```css
:root {
  color-scheme: light dark;
  --page: #f9f9f7;
  --ink: #0b0b0b;
  --font: system-ui, -apple-system, "Segoe UI", "Hiragino Sans", "Noto Sans JP", sans-serif;
}
@media (prefers-color-scheme: dark) {
  :root { --page: #0d0d0d; --ink: #ffffff; }
}
```

**色だけで区別させない。** カレンダーの凡例のように、色に加えて形か文字を
付ける。色覚と、白黒印刷と、暗い画面で同時に効く。

## フィードバック導線

**アプリの中と紹介ページの両方**に置く。片方だけだと届かない。

```ts
const REPOSITORY = "https://github.com/<<<owner>>>/<<<repo>>>";
link(t("feedback.bug"), `${REPOSITORY}/issues/new?labels=bug`, "bug");
link(t("feedback.idea"), `${REPOSITORY}/issues/new`, "idea");
```

- **不具合と要望を分ける。** ラベルを URL に埋めておけば分類が要らない
- 素の `<a>` なので、押すまで通信しない (外部通信 0 件の約束を壊さない)
- 置き場所は**目立たないが探せば必ずある**ところ (フッタ)

## 紹介ページを入口にする

いきなり道具が開くと「これは何か」「どこまで信用してよいか」が分からない。

紹介ページに置くもの:

- 1 行で何ができるか + 画面の絵
- **「通信しません」「インストール不要」**のような、不安を先に消す説明
- 道具を開くボタン / ダウンロード
- ソース・文書・**フィードバック**へのリンク

## 多言語

文字列を 1 か所のテーブルに集める (`i18n.ts`)。最初から 2 言語で書くのは
重いが、**あとから引き剥がすほうが重い**。README も英語と日本語に分ける。

配るサンプルデータは英語にする。日本語のままだと、読めない人が最初の
1 件で詰まる。
