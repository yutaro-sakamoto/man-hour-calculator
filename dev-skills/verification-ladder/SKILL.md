# 検証の段

「テストを書いた」では何も分からない。**どの約束を、どの強さで確かめて
いるか**を表にする。表があると、強さを下げる変更が目につく。

| 段 | 手段 | 分かること |
|---|---|---|
| 1 | 単体テスト | **試した入力について**正しい |
| 2 | 性質テスト (乱択) | 撃った標本の範囲で性質が崩れていない |
| 3 | 差分テスト (相互オラクル) | 独立した 2 実装が食い違っていない |
| 4 | 型による構成 | その値が存在する時点で成り立つ |
| 5 | **有界モデル検査 (Kani)** | 区間の**すべての入力**について成り立つ |
| 6 | **モデル検査 (TLC / TLA+)** | 設計として、**到達しうるすべての状態**で成り立つ |
| — | miri | FFI 層に未定義動作が無い |
| — | ミューテーションテスト | 上の検査に**歯が立っている** |

**既にある段を下げない。** 型と Kani で守っているものを「テストで確かめて
いるから」と緩めない。表 (`docs/VERIFICATION.md`) を置き、
機械で見張る ([docs-spec-drift](../docs-spec-drift/))。
`assets/VERIFICATION-template.md` に骨がある。

## 段 4: 型で先に潰す (いちばん安い)

不変条件は smart constructor (parse, don't validate) で型に載せる。

```rust
// 値が存在する時点で 0 ≤ min ≤ likely ≤ max かつ有限であることが保証される
pub struct TaskEstimate { min: f64, likely: f64, max: f64 }
impl TaskEstimate {
    pub fn new(min: f64, likely: f64, max: f64) -> Option<Self> { ... }
}
```

型に載せれば、検査は「構築できるか」だけになる。**バリデーションを
呼び忘れる筋が消える。** ここをやってから上の段に進む。

## 段 5: Kani — どこに当てるか

有界モデル検査は「区間のすべての入力」を SMT で解く。**当てる場所を
選べるかどうか**が費用を決める。

当たる (安い):

- 型の不変条件 — 「構築できた値は必ず条件を満たす」
- **その逆も** — 「妥当な入力は必ず受け付ける」(全部断る実装で通らないように)
- `NaN` がどの位置でも弾かれる
- 日付の往復 (`日数 → 年月日 → 日数` が恒等、±200 年)
- 順序関係の公理 (反射・反対称・推移・全比較)
- **バッファの寸法** — 「宣言した長さ = 区画の合計」を、受け付けうる寸法
  すべてについて
- 単調性 — 「権限を上げて、できることが減らない」を役割 × 操作の全組で

当たらない (やらない):

- **浮動小数の計算そのもの。** 逆関数やモンテカルロの収束は、SMT で解くより
  性質テスト (段 2) と差分テスト (段 3) のほうが実際的
- ループの回数が入力で決まるもの

11 ハーネスで約 45 秒。CI の 1 ジョブに収まる。

```sh
cargo kani --workspace
```

### CI で Kani を入れるときの地雷

`cargo kani setup` は自前のツールチェーンと CBMC を GitHub から取りに行き、
**ときどき 504 を返す**。Kani 自身の curl なのでこちらからリトライフラグを
足せない。**手順ごと試し直す**。

```yaml
- run: |
    cargo install --locked kani-verifier
    for attempt in 1 2 3 4 5; do
      cargo kani setup && break
      echo "::warning::kani setup が $attempt 回目で失敗" >&2
      sleep $((attempt * 15))
    done
    cargo kani --version   # 5 回とも駄目ならここで落ちる
```

## 段 6: TLA+ — 何をモデル化するか

**「操作の順序で破れる不変条件」だけ。** 1 回の操作を見ていても分からず、
誰かが筋を思いつかないとテストにならないもの。

man-hour-calculator で守りたかったのは 1 つだけ:
**「どのプロジェクトにも、実在するアカウントが所有者として必ず 1 人以上いる」**。
破れると、誰も権限を配り直せず誰も消せない。データは残るのに手が出せない。

TLC が見つけた 3 つ + レビューが見つけた 1 つ。どれも単体テストでは
思いつかれていなかった。

1. グループに所有権を預けたまま、**最後のメンバーが抜ける**
2. 入れ物から継いだ所有権だけを頼りに、**その入れ物から出る**
3. 入れ物の所有者を、**構成員の居ないグループに付け替える**
   (「付与が 1 つ残っている」ことしか見ていなかった)
4. **空の入れ物**が、実在しない所有者のまま残る (配下ごとに回る検査は、
   配下が 0 件だと 1 周もしない)

共通しているのは「**付与が残っているか**」ではなく「**実在のアカウントが
残るか**」を見なければいけない、ということ。

### 書きかた

- 仕様は**実装と同じ場所に同じ番人**を置く形にする。書き写し忘れれば TLC が
  そこを突く — それがこの仕様の役目
- 仕様のコメントで実装の関数を名指しする (`Service::set_group_member`)。
  名前が変わったら機械で検出できる
- スコープは小さく。「2 人・1 チーム・1 プロジェクト・1 入れ物」で
  4 つとも出た (小スコープ仮説)。31 万状態、数秒
- **モデル化していないものを文書に書く。** 4 番目が TLC をすり抜けたのは、
  入れ物自身の所有者をモデル化していなかったため
- 反例はそのまま**回帰テストに写す**

### `.cfg` が無いと黙って緑になる

TLA+ の一番怖い失敗はこれ。`INVARIANT` の無い `.cfg` は、何も検査せずに
成功する。機械で見張る (`docs-spec-drift` の `check-sync.sh` に入っている)。

## miri — `unsafe` のある場所だけ

`unsafe` を 1 つのクレート (FFI 層) に閉じ込めて、そこだけ miri を回す。

```sh
MIRIFLAGS=-Zmiri-strict-provenance cargo +nightly miri test -p <<<ffi-crate>>>
```

`-Zmiri-strict-provenance` は「整数から作ったポインタ」を許さない。
生ポインタをスライスに読み替える層でこそ効く。型検査もテストも、
ここだけは守ってくれない。

## ミューテーションテスト — 検査に歯があるか

カバレッジが言うのは「どの行を通ったか」で、「確かめているか」ではない。
1 か所だけ書き換えて、テストが気づくかを見る。

```sh
cargo mutants -p <<<core>>> -p <<<api>>> --timeout 60
```

- **毎日 1 回**でよい (03:00 JST)。PR ごとに回すには重い
- 4 シャードに割って並列に。`--shard` は **0 始まり** (`k < n`)。
  `1..4` と書くと `4/4` が落ちる
- `--timeout` は 1 変異あたり。無限ループに化けた変異で一晩潰さないため
- 捕捉率 = `caught / (caught + missed)`。**`unviable` と `timeout` は分母に
  入れない** — テストの落ち度ではない
- 閾値は**実測の少し下**に置く。上げるのは見逃しを潰してから
- 薄い繋ぎ (サーバのハンドラ) と FFI 境界は対象から外す。変異を入れても
  「意味のある間違い」になりにくい
- 下回ったら**見逃した変異を並べた Issue を立てる**。そこはテストが通っては
  いるが何も確かめていない箇所

## 差分テスト — 2 実装を互いのオラクルにする

同じ仕様の独立した 2 実装 (モンテカルロと数値畳み込み) を両方持ち、
答えが一致することを検査する。

**片方だけを直したくなったら、どちらかが間違っている合図。** これが
一番強い警報になった。
