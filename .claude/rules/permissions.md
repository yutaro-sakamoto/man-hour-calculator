# 権限を触るときは、仕様も一緒に動かす

守りたいのは 1 つ。**どのプロジェクトにも、実在するアカウントが所有者として
必ず 1 人以上いる。** 破れると、誰も権限を配り直せず誰も消せない状態になる。
データは残るのに手の出しようが無くなる。

この条件は**操作の順序**で破れる。「グループに所有権を預けたまま最後の
メンバーが抜ける」ような筋は、誰かが思いつかないとテストにならない。だから
[spec/Permissions.tla](../../spec/Permissions.tla) に設計を状態機械として
書いて、TLC に到達しうる状態を全部たどらせている。

## 実装に番人を足したら、仕様の同じ場所にも足す

仕様は**実装と同じ場所に同じ番人**を置いてある。書き写し忘れれば TLC が
そこを突く — それがこの仕様の役目。逆に、仕様にだけ足して実装に足さなければ、
TLC は緑のまま実物が壊れる。

```sh
./spec/check.sh        # 31 万状態、数秒
```

## 過去に見つかった穴

TLC が 3 つ、レビューが 1 つ見つけている。どれも**単体テストでは思いつかれて
いなかった**もの。新しい操作を足すときは、この形に当てはまらないか考える。

1. グループに所有権を預けたまま、最後のメンバーが抜ける (`set_group_member`)
2. 入れ物から継いだ所有権だけを頼りに、その入れ物から出る (`update_project`)
3. 入れ物の所有者を、構成員の居ないグループに付け替える (`set_group_access`)
4. **空の入れ物**が、実在しない所有者のまま残る（配下のプロジェクトごとに
   回る検査は、プロジェクトが 0 件だと 1 周もしない）

共通しているのは「**付与が残っているか**」ではなく「**実在のアカウントが
残るか**」を見なければいけない、ということ。`owner_users` を通すこと。

## 仕様の限界も書いておく

いまの仕様は「2 人・1 チーム・1 プロジェクト・1 入れ物」。所有者がグループ
経由になる筋を出すのにはこれで足りる（小スコープ仮説）。**モデル化して
いないもの**があるなら `docs/VERIFICATION.md` の「まだ届いていないところ」に
書き足す。4 番目の穴が TLC をすり抜けたのは、入れ物自身の所有者を
モデル化していなかったため。
