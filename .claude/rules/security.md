# 攻める側から考える

サーバは `tests/security.rs` が、配布物は `e2e/tests/security.spec.js` が、
悪意のある呼び手を想定して叩いている。**足したものは自動で検査に入る**ように
作ってあるので、次を崩さない。

## ルートを足すとき

`ROUTES` (`crates/api/src/protocol.rs`) に足せば、全ルートの走査
(BOLA/IDOR・401) に自動で入る。走査は id を bob の手で差し込むので、
**id を含むルートは、関係の無いアカウントからは必ず失敗する**ように書く。
一覧のように「自分の範囲だけ返す」ルートは、他人のものが混ざらないことを
別に確かめる。

## 守りの層の順番

`http.rs` の `router` の層は、外から順に「防御のヘッダ → 認証 → 本文の上限 →
ルート」。**認証は本文を読む前。** axum は本文を型に読み込むのを
ハンドラより先にやるので、ハンドラの中で認証すると、トークンの無い呼び手に
本文を読ませ、本文の形の誤り (422) を返してしまう (実際にそうなっていた)。

本文の上限 (`BODY_LIMIT`) は**正しい呼び出しの最大**から計算する。既定値の
ままだと、上限いっぱいの添付がサーバでだけ 413 で落ちていた。

## 1 つの操作は 1 回だけ書き、書いたあとは読まない

保存先は複数の対象にまたがるトランザクションを約束しない。2 回書く操作は
あいだで落ちると半端を残し、書いたあとに読む操作は、読みで落ちると
「失敗」と答えたのに書けている。`service/fuzz/chaos.rs` が構造として
見張っている。応答は書く前に組み立てる。
